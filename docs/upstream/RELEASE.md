## Справка и история предыдущего выпуска 1.0.0 (2)


Все три варианта имеют пакет `ru.kolbabot.app`, версию `1.0.0` и код версии `2` (сборка 2). Они используют один сервер `https://kolbabot.ru`, одну подпись выпуска и одинаковые функции. Канал магазина записывается в `BuildConfig.STORE_CHANNEL` и metadata `ru.kolbabot.app.DISTRIBUTION_CHANNEL`.

| Магазин | Вариант | Файл после успешной сборки |
| --- | --- | --- |
| Google Play | `googleRelease` | `app/build/outputs/bundle/googleRelease/app-google-release.aab` |

Оба APK универсальные: разделение по ABI и плотности экрана отключено. Google AAB предназначен для загрузки в Google Play; установочные APK из него формирует магазин. Приложения разных каналов не устанавливаются рядом: одинаковый пакет означает обновление одной установленной программы при совпадающей подписи. Отладочную сборку перед установкой подписанного выпуска нужно удалить, если Android сообщает о несовместимости подписей.

Каталог комплекта — `../artifacts/android/release-1.0.0-build2` относительно этой папки: AAB Google Play, два подписанных APK для RuStore и Huawei AppGallery и ZIP самостоятельного проекта Android Studio. Комплект сборки 2 сформирован из проверенных файлов обновлённого интерфейса и R8. Прежний комплект сборки 1 не является результатом этого выпуска. Ключ подписи, серверные секреты, приватный env-файл и исходный секретный экспорт Huawei в ZIP не включаются.

По умолчанию это `https://github.com/Efreitor2001/kolbabot-android-releases/releases/download/v1.0.0/KolbaBot-1.0.0-rustore.apk` и `https://github.com/Efreitor2001/kolbabot-android-releases/releases/download/v1.0.0/KolbaBot-1.0.0-huawei.apk`. Адреса заданы в серверном коде; параметры запроса, локальные файлы и переменные окружения их не меняют. Публичные APK должны быть доступны до выпуска обновлённой веб-страницы.

Для публичных и приватных assets используются соответствующие наборы контрольных сумм: публичный список не должен ссылаться на недоступные исходники или карты R8. При обновлении только README/RELEASE можно заново упаковать исходный ZIP и пересчитать его SHA-256 без пересборки APK/AAB; прежние бинарники и их контрольные суммы сохраняются.

Наличие подписанных файлов и их размещение на GitHub не гарантируют одобрение Google Play, RuStore или Huawei AppGallery. Загрузка в консоли магазинов, оформление карточек и модерация выполняются отдельно.

Локальная инструкция по заполнению карточек магазинов: [KolbaBot-store-forms.html](../artifacts/android/store-submission/KolbaBot-store-forms.html) и [KolbaBot-store-forms.txt](../artifacts/android/store-submission/KolbaBot-store-forms.txt).

Перед выбором других стран распространения нужно отдельно проверить применимые требования Google Play и необходимые изменения платежной схемы. ## Ограничение RuStore: удаление аккаунта

По [пункту 5.4 официальных требований RuStore](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/requirement-apps), проверенному 15 октября 2026 года, приложение с регистрацией должно предоставлять удаление аккаунта непосредственно в приложении и удаление либо обезличивание связанных персональных данных. Единственным способом не может быть обращение в поддержку или запрос по email.

В текущей версии `/android/delete-account` открывает подготовленное письмо на `obolo4ki@kolbabot.ru`; встроенного сценария удаления аккаунта нет. Это известное ограничение выпуска `1.0.0`: перед отправкой в RuStore нужно реализовать и проверить удаление внутри приложения с соответствующей серверной обработкой. Готовый APK `rustoreRelease` не означает выполнение этого требования или прохождение модерации.

## Внешний ключ подписи

Ключ Колбабота хранится вне проекта. Стандартное расположение настройки на Windows:

```text
%LOCALAPPDATA%/KolbaBot/signing/signing.properties
```

Файл содержит четыре поля Java Properties:

```properties
storeFile=C:/Users/USERNAME/AppData/Local/KolbaBot/signing/kolbabot-release.jks
storePassword=YOUR_STORE_PASSWORD
keyAlias=kolbabot
keyPassword=YOUR_KEY_PASSWORD
```

В `storeFile` нужен абсолютный путь; прямые слеши устраняют неоднозначность escape-последовательностей Java Properties. Пример содержит заполнители, а не действующие пароли. Для другого расположения задайте переменную окружения `KOLBABOT_SIGNING_PROPERTIES` с абсолютным путём к файлу. На Linux/macOS стандартный путь — `~/.config/KolbaBot/signing/signing.properties`.

Сборка проверяет, что файл настройки и сам ключ находятся вне исходного проекта. Без полного файла настройки и существующего ключа выпуск завершается ошибкой; подмена подписью отладки не выполняется. Пароли не передаются аргументами команд и не входят в APK, AAB, исходники или архив проекта. Ключ и пароли нужно сохранить в защищённой резервной копии: они нужны для последующих обновлений. Не создавайте новый ключ для каждого выпуска и не используйте ключи других приложений.

## Сборка и проверки

В PowerShell из папки `android`:

```powershell
.\build.ps1 -Check -DeviceTests
.\build.ps1 -Release
```

Первая команда проверяет `googleDebug`: сборку, JVM-тесты, Android Lint и инструментальные тесты на подключённом устройстве/эмуляторе. Вторая создаёт три подписанных файла из таблицы и выполняет Lint для каждого варианта выпуска. Если нужны оба этапа одним запуском, используйте `-Release -Check -DeviceTests`.

Без PowerShell доступны отдельные задачи Gradle с тем же внешним файлом подписи:

```text
./gradlew :app:bundleGoogleRelease :app:assembleRustoreRelease :app:assembleHuaweiRelease :app:lintGoogleRelease :app:lintRustoreRelease :app:lintHuaweiRelease
```

R8 включён во всех вариантах выпуска вместе с удалением неиспользуемых ресурсов. Используются оптимизирующие правила Android и consumer rules подключённых SDK; приложение не отключает оптимизацию общими `-keep` или `-dontwarn`. JVM-тесты и инструментальные тесты отладочной сборки не заменяют проверку запуска подписанных APK после R8 на целевых устройствах.

Для Huawei Network Kit явно подключена `bcprov-jdk15to18:1.86`: SDK включает AES/SP800 генератор случайных чисел и обращается к классам Bouncy Castle. Отсутствие криптографических классов не подавляется. В `proguard-rules.pro` перечислены только конкретные необязательные классы расширений Huawei OS и отдельного HiAnalytics SDK: их наличие проверяет сам SDK, предусмотрены штатные запасные пути. Правила не отключают проверки остальных классов или оптимизацию.

С каждым опубликованным файлом сохраните соответствующую карту R8:

```text
app/build/outputs/mapping/googleRelease/mapping.txt
app/build/outputs/mapping/rustoreRelease/mapping.txt
app/build/outputs/mapping/huaweiRelease/mapping.txt
```

Для следующего выпуска увеличивайте `versionCode` в `app/build.gradle.kts`; магазины используют его для порядка обновлений. Настройки Google Play App Signing и сертификат, которым магазин подписывает установку, проверяются отдельно в консоли магазина.

## Конфигурация push для выпуска

Все варианты включают Firebase и Huawei Push Kit; доступный транспорт выбирается на устройстве. Файл `app/google-services.json` содержит клиентскую конфигурацию Firebase. Серверный сервисный аккаунт Firebase и серверные секреты Huawei остаются вне приложения.

Аналитика Google/Firebase отключена через `firebase_analytics_collection_enabled=false`, служебная BI-аналитика Huawei — через `com.huawei.hms.client.bi.setting=true`. Значение `true` у этой настройки Huawei отключает сбор. Автоматическая инициализация FCM и HMS также отключена. Перед передачей итогового комплекта нужно проверить эти значения в объединённом манифесте каждого release-варианта и проверить запуск последней сборки; более ранняя проверка APK не подтверждает последующие изменения.

Для HMS поместите клиентский экспорт Huawei в `app/agconnect-services.json`: требуется `client.app_id` из 5–64 цифр и точное значение `client.package_name=ru.kolbabot.app`. При отсутствии или некорректной конфигурации `HAS_HUAWEI_CONFIG=false`, Huawei Push не активируется. Исходный экспорт исключён из Git и не должен попадать в архив исходников, потому что может содержать секреты. Для воспроизводимой сборки архив проекта может включать только очищенный файл с тем же именем и перечисленными ниже публичными полями.

Задача `generateHuaweiAssets` создаёт `kolbabot-huawei.json` только из публичных полей: `configuration_version`, `region`, адресов `agcgw.url/backurl` и `client.app_id/package_name/cp_id/project_id/api_key/product_id/client_id`. Поля `client_secret`, `oauth_client`, закрытые ключи и остальной экспорт в APK не копируются. Оригинал не находится в каталоге Android assets. Плагин AGCP не требуется: адаптер устанавливает этот ограниченный набор через `AGConnectServicesConfig.setParam`, в том числе если SDK уже прочитал настройки ранее. Huawei Push, AAID и OpenDevice поставляют consumer rules внутри AAR; широкие дополнительные исключения R8 не добавляются.

Для реальной доставки нужна также серверная настройка соответствующего провайдера и разрешение уведомлений на телефоне. Наличие готового APK само по себе не подтверждает настройку Huawei AppGallery Connect, серверную доставку или публикацию в магазине.

В отдельном предыдущем опыте до сборки 2 FCM был проверен реальной отправкой и получением уведомления на эмуляторе в фоне. Это не проверка нынешнего APK или очереди рабочего сайта. Для Huawei подтверждена только серверная OAuth-авторизация HTTP 200; доставка на реальное Huawei-устройство ещё не проверялась. Подробности и подтверждающие файлы приведены в [README.md](README.md#проверки-и-границы).

## Передача серверного кода и переменные

Серверный код передан в Git Amvera через [GitHub Actions](https://github.com/Efreitor2001/kolbabot.ru/actions/runs/38781833933): запуск завершился **SUCCESS**, включая шаг **Push to Amvera**. Workflow `.github/workflows/sync-amvera.yml` переведён с `msk0` на `msk1` коммитом `0bccba868ad287df26147abb48bb154d0faaf531`, опубликованным в GitHub `main`. Это подтверждает передачу Git-кода, но не успешную сборку и запуск контейнера. Состояние production-контейнера, `/api/health` и доступность новых страниц из внешней сети пока не подтверждены: прямые и веб-проверки из текущей среды недоступны. Серверные переменные пользователь настраивает самостоятельно. GitHub Release с установочными файлами не заменяет проверку серверного развёртывания. В репозиторий Amvera передаются изменения сайта и `static/android`; Android-проект и бинарники исключены из Git и контейнера.

Готовый приватный файл `%LOCALAPPDATA%\KolbaBot\secrets\amvera-android-push.env` содержит три строки. В существующем приложении Amvera первые две добавляются как **секреты**, последняя — как обычная переменная:

1. `MINIAPP_FCM_SERVICE_ACCOUNT_BASE64` — значение из готового файла.
2. `MINIAPP_HMS_CREDENTIALS_BASE64` — значение из готового файла.
3. `MINIAPP_ANDROID_PUSH_ENABLED=1`.

Существующие `MINIAPP_DATA_ENCRYPTION_KEY`, `MINIAPP_CSRF_SECRET`, реквизиты БД, оплаты и OAuth, а также `/data` сохраняются без замены. После изменения переменных нужен новый запуск контейнера; само добавление переменных не обновляет backend. Проверка сборки и запуска контейнера Amvera выполняется отдельно от успешного Git push и сборки APK/AAB. Затем установите новый APK, войдите в аккаунт, включите уведомления и разрешите системный запрос, дождитесь успешной регистрации и только после этого создайте новое уведомление для проверки. Старые сообщения при первой регистрации не рассылаются. Пока запуск нового backend и его настройки не подтверждены, нативный push может оставаться недоступным; браузерное уведомление его не подтверждает. Полная инструкция находится в [README.md](README.md#ручной-перенос-трёх-переменных-в-amvera).
