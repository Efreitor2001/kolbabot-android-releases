# Колбабот для Android

Самостоятельный проект Android Studio: Kotlin, Jetpack Compose, Android 8.0+ (API 26), целевой API 37. Основной интерфейс нативный, WebView не используется. Сервер по умолчанию — `https://kolbabot.ru`. Текущие исходники: версия `1.0.1`, `versionCode=3` (сборка 3). Основа — опубликованный 15 октября 2026 года проект `1.0.0 (2)`. Debug APK этой версии собраны в GitHub Actions; release APK/AAB не выпускались. Изменения и статус проверок — в [CHANGELOG.md](CHANGELOG.md) и [CI.md](CI.md).

## Возможности

- Каталог с поиском, раскрываемыми категориями, компактными строками товаров, вариантами, карточками и отзывами. Единое оформление списков, карточек и цветных плашек использует палитру сайта.
- Карусель баннеров с прокруткой пальцем, переключателями и автоматической сменой. Старый сервер поддерживается: приложение отображает существующие три акции из прежнего ответа API.
- Серверная корзина, колбаски, поиск ПВЗ Ozon, расчёт доставки, оформление физических и цифровых товаров, история и состояние заказов. Заказы сгруппированы в раскрываемые списки с цветными статусами; состав и действия открываются из выбранного заказа.
- Оплата через существующий Т-Банк в браузере; возврат в приложение обновляет состояние. Незавершённый заказ и ключ повторного запроса сохраняются, автоматического повторного списания нет.
- Рецепты, выбор вариантов ингредиентов, серверный расчёт партии и себестоимости, пользовательские цены, ингредиенты в корзину, экспорт PDF через меню Android.
- Собственный редактируемый расчёт, справочник, оборудование, FAQ, статьи, комментарии, ответы и реакции.
- Вход по логину, регистрация с подтверждением почты, восстановление пароля, второй фактор. Google/VK/Mail.ru/ОК используют существующий вход сайта через описанный ниже переход.
- Кабинет: подписка и проверка промокода, сохранённый способ оплаты, отключение автопродления, подтверждение и повторная отправка кода почты, баланс колбасок, привязанные способы входа, реферальная ссылка, уведомления, обращения в поддержку.
- Настоящие push-уведомления через Firebase Cloud Messaging (FCM) или Huawei Push Kit (HMS), с запросом системного разрешения при первом запуске, ещё до входа. Настройка приложения по умолчанию включена для каждого аккаунта; после подтверждённого входа регистрация запускается автоматически при наличии разрешения Android. Дополнительного приглашения после входа нет. Отказ в системном запросе не вызывает повторных автоматических запросов; повторить его можно в кабинете. Ручное отключение в кабинете сохраняется для этого аккаунта на устройстве; статус подключения показывает результат серверной регистрации. Сервер отправляет новые сообщения из существующего раздела уведомлений; нажатие открывает этот раздел в приложении. Периодического опроса сообщений телефоном нет; WorkManager повторяет только регистрацию устройства при сбоях сети. Выход и смена аккаунта выключают прежнюю привязку. Для доставки нужны настройки выбранного провайдера на сервере и в приложении, работающие Google Play Services или Huawei HMS Core и разрешение уведомлений на телефоне. Канал без настроек отображается как недоступный.
- Выбор пользователя в админке — общий выпадающий список с поиском по имени, логину, почте, телефону или ID: профили, личные оповещения, назначение существующего администратора, журналы базы данных и безопасности. В списке показываются имя, логин, почта и ID; поиск по ID может загрузить пользователя вне первых 2000 записей сервера.
- Полная нативная админка: обзор показателей, заказы и возвраты, корзины, товары и варианты, категории, доставка и акции, электронные книги и очередь отправки, отзывы, рецепты и состав, справочник, статьи с редактором текста, FAQ, оборудование, пользователи и доступ, обращения и оповещения, журналы, аналитика и настройки. Доступ: **Ещё → Админ** — самостоятельный раздел, не вложенный в кабинет. Пункт виден только после свежей проверки прав; сам раздел проверяет их повторно. Для администратора без 2FA есть подключение одноразовых кодов.
- В административных заказах номер, ФИО, телефон, почта, адрес, реквизиты оплаты, товары и другие значения копируются отдельным нажатием; приложение подтверждает копирование. Адрес копируется полностью, включая переносы строк. Почту аккаунта можно дополнительно получить из профиля покупателя.
- Системная кнопка «Назад» последовательно закрывает диалог, вложенный экран, раскрытые данные или поиск; из админки возвращает в предыдущий раздел. Ввод с открытой клавиатурой сначала закрывает клавиатуру штатными средствами Android. На главной странице остаётся обычный выход без дополнительного диалога.
- Нативный редактор баннеров: редактирование существующих, добавление, удаление с подтверждением, порядок, видимость, изображение по HTTPS URL, ссылка и подпись кнопки, предпросмотр.
- Загрузка фото, книг и файлов импорта через системный выбор файлов; получение PDF, Excel и автономного HTML товарного чека через системное меню сохранения/отправки. Работа с заказами и административными формами не требует открытия сайта.

## Открыть и собрать

В Android Studio выберите **Open** и эту папку `android` (файл `settings.gradle.kts`). Установите Android SDK Platform 37. Используются AGP 9.3.3, Gradle 9.7.1 и JDK 21 из Android Studio; Wrapper включён.

Windows:

```powershell
.\build.ps1
.\build.ps1 -Check
.\build.ps1 -Check -DeviceTests
```

Последняя команда требует запущенного Android-эмулятора или подключённого телефона с разрешённой отладкой. Скрипт применяет обход проблемы Unix-сокетов JBR на этом Windows-ПК только для процесса сборки и восстанавливает переменные окружения. Настройки сети компьютера не меняет.

APK для проверки: `app/build/outputs/apk/google/debug/app-google-debug.apk`. Обычная сборка и команды проверок используют вариант `googleDebug` с отладочной подписью. Для магазинов подготовлены варианты `google`, `rustore` и `huawei`: Google AAB и два универсальных APK с R8 и удалением неиспользуемых ресурсов. Команда выпуска — `./build.ps1 -Release`; настройка внешнего ключа, выходные файлы и правила сохранения карт R8 описаны в [RELEASE.md](RELEASE.md). Ключи и пароли в проект не включаются.

Исторический комплект версии 1.0.0 (2) — `../artifacts/android/release-1.0.0-build2`: AAB для Google Play, подписанные APK для RuStore и Huawei AppGallery, ZIP самостоятельного проекта Android Studio. Сборка 2 опубликована 15 октября 2026 года. Для сборки 3 сформированы три debug APK, доступные в артефактах GitHub Actions; это не новые релизные бинарники.

Предыдущий опубликованный выпуск `1.0.0 (2)` находится по двум адресам:

- [Публичный выпуск с APK и AAB](https://github.com/Efreitor2001/kolbabot-android-releases/releases/tag/v1.0.0): `KolbaBot-1.0.0-rustore.apk`, `KolbaBot-1.0.0-huawei.apk` и `KolbaBot-1.0.0-google.aab`.

Эти адреса относятся к предыдущей версии и не содержат правки сборки 3. Версию нового бинарника после сборки необходимо проверять по `versionCode=3` и собственным контрольным суммам. Для RuStore остаётся необходимая доработка удаления аккаунта внутри приложения: текущий запрос по email недостаточен. Подробности — в [RELEASE.md](RELEASE.md#ограничение-rustore-удаление-аккаунта).

Это не подтверждает соответствие существующей оплаты книг и PREMIUM через Т-Банк правилам магазина во всех странах. ## Подключения и безопасность

Приложение обращается к тому же HTTP API, что сайт. База PostgreSQL, Т-Банк, Ozon Delivery, SMTP, Google/VK и настройки акций остаются на сервере. `.env`, реквизиты БД, платёжные секреты и OAuth client secrets не копируются в APK.

Используются обычная серверная HttpOnly cookie-сессия и `X-CSRF-Token`. При ротации сессии приоритет имеет новый токен заголовка. Сессия сохраняется с AES-GCM и ключом Android Keystore. Копирование данных приложения в облако и перенос на другое устройство отключены, включая черновики оформления. Проверка TLS стандартная; HTTP и перенаправление запросов API на другой домен запрещены. User-Agent стабилен между версиями, чтобы серверная привязка сессии не сбрасывалась при обновлении.

Сбор аналитики Google/Firebase и служебной BI-аналитики Huawei отключён настройками приложения. В манифесте установлены `firebase_analytics_collection_enabled=false` и `com.huawei.hms.client.bi.setting=true` — у Huawei значение `true` означает отключение. Автоматическая инициализация push также выключена; подключение уведомлений выполняется после согласия пользователя в кабинете. Эти настройки не отменяют обмен данными, необходимый для выбранного push-провайдера.

Цены и права доступа определяет сервер. Предварительные суммы на экране не заменяют проверку заказа сервером. Реальные платежи, отправка писем и изменение каталога во время разработки не выполнялись.

## Настройка push-уведомлений

Все три магазинных варианта содержат FCM и HMS. При новом подключении приложение предпочитает настроенный FCM на устройстве с работающими Google Play Services; если он недоступен, использует настроенный Huawei Push Kit при наличии HMS Core. Установленная привязка сохраняет своего провайдера. На Android без обеих служб системная доставка push недоступна; сообщения остаются в личном кабинете. Само название варианта `huawei` не включает HMS автоматически.

### Статус передачи серверного кода

Серверный код передан в Git Amvera через [GitHub Actions](https://github.com/Efreitor2001/kolbabot.ru/actions/runs/38781833933): запуск завершился **SUCCESS**, включая шаг **Push to Amvera**. Workflow `.github/workflows/sync-amvera.yml` переведён с `msk0` на `msk1` коммитом `0bccba868ad287df26147abb48bb154d0faaf531`, опубликованным в GitHub `main`. Это подтверждает передачу Git-кода, но не успешную сборку и запуск контейнера. Состояние production-контейнера, `/api/health` и доступность новых страниц из внешней сети пока не подтверждены: прямые и веб-проверки из текущей среды недоступны. Серверные переменные пользователь настраивает самостоятельно.

### Ручной перенос трёх переменных в Amvera

Готовый приватный файл с действующими значениями находится вне проекта: `%LOCALAPPDATA%\KolbaBot\secrets\amvera-android-push.env`. Значения переменных пользователь переносит в Amvera самостоятельно; успешная передача кода через Actions не подтверждает, что они уже применены. Для нативного push нужны запущенный обновлённый backend и корректные настройки выбранного провайдера.

В существующем приложении Amvera, в разделе переменных:

1. Добавьте **секрет** `MINIAPP_FCM_SERVICE_ACCOUNT_BASE64`, скопировав его значение из готового файла.
2. Добавьте **секрет** `MINIAPP_HMS_CREDENTIALS_BASE64`, скопировав его значение из того же файла.
3. Добавьте обычную переменную `MINIAPP_ANDROID_PUSH_ENABLED` со значением `1`.

Сохраните действующие `MINIAPP_DATA_ENCRYPTION_KEY`, `MINIAPP_CSRF_SECRET`, настройки БД, оплаты и OAuth без замены; существующий каталог `/data` также сохраняется. `MINIAPP_FCM_PROJECT_ID` необязателен: проект указан в ключе Firebase. Значения Base64 имеют приоритет над соответствующими `*_FILE`. Приватный файл не включается в Git, APK или архив проекта. Переменные применяются при следующем запуске контейнера: добавьте их перед выпуском обновлённого backend либо перезапустите контейнер после изменения настроек. Само добавление переменных не обновляет серверный код.

### Проверка после запуска обновлённого сервера

1. Проверьте в Amvera завершение сборки и запуск переданного backend с зависимостями и миграцией регистрации устройств. Добавьте три переменные выше и перезапустите контейнер, если они ещё не применены. Существующие секреты и данные сохраняются.
2. Установите новый APK сборки 2 поверх приложения с той же подписью, войдите в свой аккаунт и нажмите «Включить» в приглашении уведомлений либо в кабинете. На Android 13+ разрешите системный запрос; если разрешение уже выдано, повторный диалог не требуется.
3. Дождитесь успешного статуса подключения уведомлений приложения. Ошибка регистрации или недоступный сервер не означают подключение, даже если Android уже дал разрешение.
4. Только после подключения создайте **новое уведомление** для этого аккаунта через сайт. Старые сообщения при первой регистрации не рассылаются. Сверните приложение и проверьте системное уведомление и переход из него в кабинет.

До запуска обновлённого backend и применения его настроек нативный push может оставаться недоступным. Уведомление в браузере подтверждает отдельный канал web push, а не регистрацию Android-приложения. GitHub Release и установка APK сами по себе не устанавливают серверные изменения; успешный Git push не заменяет проверку контейнера.

### Firebase

Firebase-проект — `kolbabot-9591f`, тариф Spark; Android-приложение — `ru.kolbabot.app`. Файл `app/google-services.json` уже добавлен и проверен на соответствие проекту и пакету. Это клиентская конфигурация Firebase, не закрытый ключ серверного аккаунта. Серверный ключ создан и сохранён локально вне репозитория: `%LOCALAPPDATA%\KolbaBot\secrets\fcm-service-account.json`. Наличие этого файла на ПК не подтверждает настройку хостинга.

**Отдельный предыдущий опыт, до сборки 2.** 15 октября 2026 года реальная проверка FCM повторена после добавления HMS: **2 отдельных теста прошли**. `android_push.FcmSender` получил HTTP 200 от FCM, а эмулятор с Google Play зарегистрировал нативное уведомление через Android `NotificationManager`, когда был открыт домашний экран и приложение находилось в фоне. Использовался изолированный тестовый пользователь `900000999`; тест не менял рабочие аккаунты сайта. Сохранённые подтверждения того опыта без токенов: [`fcm-send-final-verification.json`](../artifacts/android/fcm-send-final-verification.json) и [`fcm-received-final-verification.json`](../artifacts/android/fcm-received-final-verification.json). Эта прежняя проверка подтверждает транспорт FCM до эмулятора, но не валидирует сборку 2; очередь рабочего сервера и целевой телефон требуют отдельной проверки после выпуска.

Серверный шаблон находится в [`../android-push.env.example`](../android-push.env.example). Для серверного выпуска:

1. Разместите JSON сервисного аккаунта вне репозитория, предпочтительно в хранилище секретов хостинга, и задайте его путь в `MINIAPP_FCM_SERVICE_ACCOUNT_FILE`. Альтернатива — `MINIAPP_FCM_SERVICE_ACCOUNT_BASE64`; если заданы обе переменные, Base64 имеет приоритет. Закрытый ключ нельзя помещать в `google-services.json`, APK или коммит.
2. При необходимости задайте `MINIAPP_FCM_PROJECT_ID=kolbabot-9591f`; без этой переменной используется `project_id` серверного ключа. Сохраните действующий `MINIAPP_DATA_ENCRYPTION_KEY`: им шифруются токены устройств в БД, заменять его для FCM не нужно.
3. Убедитесь, что переданный обновлённый backend с зависимостями запущен, и включите `MINIAPP_ANDROID_PUSH_ENABLED=1`. Это общий выключатель FCM и HMS. По умолчанию в шаблоне стоит `0`; каждый провайдер без собственных корректных реквизитов остаётся выключенным.
4. На целевом телефоне разрешите уведомления при запуске и отдельно проверьте доставку, открытие уведомления, выход и смену аккаунта. Локальные тесты не заменяют эту проверку.

### Huawei Push Kit (HMS)

Клиент и сервер настраиваются отдельно. Идентификаторы и секреты Huawei нельзя заменять выдуманными значениями или данными Firebase.

1. В AppGallery Connect зарегистрируйте Android-приложение с пакетом `ru.kolbabot.app`, включите Push Kit, задайте расположение обработки данных и зарегистрируйте SHA-256 сертификата, которым подписан устанавливаемый APK. Для проверки debug и выпуска могут потребоваться разные отпечатки. Подготовка приложения описана в [официальном примере Huawei](https://github.com/HMS-Core/hms-push-clientdemo-android).
2. Скачайте клиентский экспорт в `app/agconnect-services.json`. Требуются `client.app_id` из 5–64 цифр и `client.package_name=ru.kolbabot.app`. После изменения файла пересоберите приложение. При его отсутствии или неверном пакете сборка работает с `HAS_HUAWEI_CONFIG=false`, а HMS остаётся недоступным.
3. Gradle создаёт `assets/kolbabot-huawei.json` только из разрешённых публичных полей; исходный экспорт, `client_secret`, `oauth_client` и закрытые ключи в APK не входят. Плагин AGCP не используется: адаптер передаёт очищенные параметры через `AGConnectServicesConfig.setParam`. Состав разрешённых полей и правила архива проекта — в [RELEASE.md](RELEASE.md#конфигурация-push-для-выпуска).

### Контракт приложения и сервера

Все ответы имеют стандартную оболочку `{"ok":true,"data":...}`. В таблице показано содержимое `data`; `ApiClient` снимает оболочку. Нужна текущая cookie-сессия, для POST/DELETE дополнительно требуется `X-CSRF-Token`. Переданный клиентом `user_id` не определяет владельца регистрации.

| Запрос | Данные и результат |
| --- | --- |
| `GET /api/android/push/config` | FCM: `{enabled, project_id}`. Старый контракт сохранён. |
| `GET /api/android/push/config?provider=huawei` | HMS: `{enabled, app_id}`. Приложение сверяет идентификатор с клиентской конфигурацией. |
| `POST /api/android/push/token` | JSON: `token`, `installation_id`, необязательный `provider` (`firebase` по умолчанию или `huawei`). Результат: `{registered:true}`. Для ненастроенного провайдера — HTTP 503. |
| `DELETE /api/android/push/token` | Те же поля. Результат: `{removed:true}`. Доступно и при выключенной доставке; удаляется только точное совпадение текущего аккаунта, установки, токена и провайдера. |

Одна установка имеет одну действующую привязку провайдера. Смена аккаунта или провайдера обновляет её атомарно; устаревший запрос удаления не снимает новую регистрацию. Миграция добавляет к `miniapp_android_push_tokens` поле `provider` со значением `firebase` для существующих записей, сохраняя старые токены и их хэши. Токены хранятся зашифрованными; лимит — 10 установок и 60 запросов регистрации в час на аккаунт.

Оба провайдера получают data-only сообщение со строковыми `user_id`, `notification_id`, `title`, `body`, `action_url`. В FCM `data` — объект, в HMS — JSON-строка. Android сверяет провайдера, настройку уведомлений, системное разрешение и привязку получателя, затем удаляет дубли по паре аккаунт/уведомление. Срок доставки — не более 24 часов; само сообщение остаётся в кабинете и после этого срока. Новая регистрация аккаунта начинает с текущего положения списка, без отправки старых сообщений. Телефон не опрашивает сервер ради доставки; WorkManager повторяет только регистрацию токена. Push-сервисы, сеть и ограничения ОС могут задерживать сообщения.

Выход или выключение уведомлений немедленно запрещает их локальный показ и отменяет показанные уведомления, затем приложение пытается удалить точную серверную привязку. Недоступность сети не отменяет локальное отключение. При смене токена регистрируется его новая версия; старый провайдер не может использовать привязку нового.

## Обновление серверной части

Перечисленные серверные модули переданы в Git Amvera успешным шагом Actions; состояние запущенного контейнера и публичных страниц ещё нужно проверить. Состав серверного изменения:

1. `mobile_auth.py` и его подключение в `app.py` — переход из браузерного входа в нативное приложение. Старт отдаёт одноразовый идентификатор и код сверки; браузер запрашивает подтверждение пользователя; приложение получает отдельную сессию по S256/PKCE. Пароли, cookie и session token не передаются в URL. Запрос живёт 5 минут и используется один раз. Привязка Google/VK/Mail.ru/ОК запускается отдельным запросом `/api/mobile/account-link/start`, закреплённым за текущим пользователем: в браузере требуется тот же аккаунт и отдельное подтверждение. Этот переход не создаёт и не передаёт новую сессию. При старой версии сервера приложение сообщает о недоступности новых переходов; вход по логину работает через прежний API.
2. `store_banners.py`, маршруты в `app.py`, веб-редактор в `admin.html`, обновлённые JS/CSS и версия ресурсов `20261015-native-banners-1` — общий редактор и карусель.
3. Дополнения `PATCH /api/admin/store/products/{id}` и `database.py` — изменение только связей товара без перезаписи карточки; сохранение дополнительных категорий и исходного форматирования неизменённого описания при редактировании через Android. Остальные административные действия используют существующие API сайта.
4. `android_push.py`, подключение его маршрутов и фоновой отправки в `app.py`, зависимость `google-auth` — серверная доставка FCM/HMS из существующих уведомлений. Добавляется таблица `miniapp_android_push_tokens` для зашифрованных токенов, привязки установки, провайдера и состояния доставки. Маршруты `/api/android/push/config` и `/api/android/push/token` используют текущую авторизацию, а изменение регистрации — также CSRF.
5. `android_pages.py`, подключение маршрутов в `app.py` и ресурсы `static/android` — страница приложения `/android`, отдельная политика `/android/privacy` и запрос удаления аккаунта `/android/delete-account` на русском, английском и упрощённом китайском. Два фиксированных маршрута скачивания перенаправляют на APK публичного GitHub Release `v1.0.0`; произвольный URL или локальный файл выбрать нельзя. Перед выпуском страницы оба APK должны быть опубликованы. Переменные окружения и локальные APK для скачивания не нужны; `android-site.env.example` содержит только пояснения. AAB доступен отдельно в публичном GitHub Release и не имеет маршрута скачивания на сайте.

Android-проект и бинарники остаются вне Git-веток сайта и образа Amvera: в корневых `.gitignore` и `.dockerignore` исключены `/android/`, `/artifacts/android/` и `/releases/android/`. Исходники Android передаются архивом в приватном Release. Серверные модули и веб-ресурсы `static/android` входят в репозиторий сайта и переданы через workflow синхронизации. Публикация установочных файлов в GitHub Release не равна развёртыванию backend; серверные push-переменные настраиваются отдельно.

Запросы мобильного входа и привязки способов входа хранятся в памяти одного серверного процесса. Перезапуск отменяет незавершённый переход. Для нескольких воркеров/реплик нужно общее хранилище либо маршрутизация всех этапов одного перехода к одному процессу. Текущие пользовательские сессии по-прежнему хранятся штатно в БД. Браузер и приложение имеют отдельные сессии: при привязке другого браузерного аккаунта сервер откажет и предложит войти в нужный. Google открывает штатный OAuth, а VK/Mail.ru/ОК завершают привязку через существующий интерфейс кабинета сайта. Оплата также остаётся в защищённой форме банка в браузере.

Схема БД для баннеров не меняется: JSON находится в существующей `store_settings`, ключ `store_banners_v1`. Пока настройки не сохранены, используются исходные три баннера с действующими значениями акций. Сохранённый пустой список действительно отключает карусель. Редактор требует текущую ревизию; при одновременном изменении возвращается 409, локальный черновик сохраняется. Изменение текста баннера не меняет правила начисления бонусов.

Веб-редактор: **Админка → магазин → Акции → Баннеры магазина**. Android: **Ещё → Админ → Баннеры**. API `GET/PUT /api/admin/store/banners` использует существующую проверку администратора, 2FA и CSRF. Публичные данные приходят в `GET /api/store` как `banners`.

Поддержаны переменные `{standard_percent}`, `{premium_percent}`, `{max_redemption_percent}`, `{referral_percent}`, `{referral_max_sausages}`, `{review_bonus_sausages}`, `{review_min_chars}`. Их заменяет сервер. Изображения задаются ссылкой/существующим путём; отдельной загрузки файлов в редакторе нет.
